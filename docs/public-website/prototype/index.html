    A-01 / Product

    State first. Scope second.

    A future product page should distinguish purpose, available behavior, limited behavior, planned work, and research. It should never turn a roadmap into a release claim.

    Prototype statement Andreja is described in repository planning as a user-owned personal assistant and skill platform. This prototype does not claim that a public product or managed service is available.
    • ExplainHuman agency, data ownership, capability boundaries, and how evidence is reviewed.
    • LabelAvailability and version on every capability; limitations sit beside the relevant statement.
    • WithholdSecurity, privacy, accessibility, performance, customer, pricing, and compatibility claims until current evidence exists.

    A-02 / Get started

    Separate paths, honest entry.

    Getting-started guidance should branch by a supported deployment mode and version. A path is published only after its prerequisites, recovery, update, and troubleshooting journey have been exercised.

    Self-host operatorRequirements, verified artifacts, setup, keys, backup, updates, recovery.
    Managed userShown only after managed availability, terms, support, privacy, and recovery are approved.
    DeveloperVersioned contracts, examples, conformance, compatibility, and security boundaries.

    No sign-in or launch button belongs on the public/help site itself. Product entry points, if later approved, remain ordinary external links to a separately operated application boundary.

    A-03 / Documentation

    A version is part of every answer.

    Canonical documentation is reviewed source that builds with the site. Search results, route metadata, release notes, and help pages show the product or contract version they apply to.

    • User and operator journeys for identity, assistant, skills, channels, sharing, backup/export, and recovery
    • Versioned API, skill, channel, and federation documentation with compatibility boundaries
    • Tested links, owned pages, review dates, expiry triggers, and known limitations
    • Locale-ready templates, metadata, navigation, search partitions, text expansion, and reading order

    A convenience “latest” route can help navigation, but immutable version routes remain addressable and canonical for historical releases.

    A-04 / Help

    Help without hidden intake.

    Searchable help, known issues, release notes, safe diagnostics, and escalation guidance can remain static. Collecting feedback cannot.

    • Release notesVersion, date, behavior changes, migration, compatibility, security relevance, and rollback guidance.
    • Known issuesImpact, affected version, safe workaround, owner, and next review without unsupported resolution dates.
    • DiagnosticsExplain what may be shared, what must never be submitted, and how preview/consent works.
    • FeedbackAbsent until a separately deployed tenant-less intake service, privacy notice, retention, abuse controls, and status flow are approved.

    A-05 / Trust boundary

    Public content, isolated delivery.

    The recommended artifact is generated ahead of time and deployed independently. Search runs over public content in the browser. The site does not query the authenticated app.

    • InsideReviewed public pages, static assets, version metadata, and a pre-generated public-content search index.
    • OutsideSign-in, app cookies, user tokens, tenant data, tasks, prompts, connector content, feedback records, analytics, and sponsorship.
    • SeparateDeployment identity, origin, hostname, request logs, cache, previews, budget, incidents, and rollback.
    Security reporting is a launch gate The future site needs an approved private reporting route and a tested /.well-known/security.txt. This prototype intentionally invents neither a contact address nor a response promise.

    A-06 / Accessibility

    A target is not a conformance claim.

    WCAG 2.2 Level AA is the intended engineering target. Public conformance wording waits for version-scoped automated and manual evidence across real pages, content, themes, devices, and assistive technology.

    • Semantic landmarks and headings, labeled controls, skip navigation, and logical focus order
    • Keyboard operation, visible focus, announced search status, and non-search navigation
    • Contrast, 320 CSS-pixel reflow, 200% text resize, target size, forced colors, and reduced motion
    • Manual screen-reader, 400% zoom, cognitive, locale expansion, and bidirectional-content review

    Automated prototype checks are useful regression evidence. They do not replace review by people using the relevant interaction modes.

    A-07 / Support & legal

    Do not invent the last mile.

    Contact, legal, license, privacy, domain, sponsorship, and support details look small on a page but carry real obligations. Placeholder prose must never escape a private prototype.

    • SupportPublish only tested safe routes, prohibited-content guidance, tracking expectations, and capacity-backed response language.
    • LegalWait for approved ownership, license, terms, privacy notice, mark, and domain decisions.
    • SponsorshipRemain absent until policy, legal/tax/payment, disclosure, and relationship gates are satisfied.

    For now, repository documentation and issue #94 are the source of this planning work. They are not public support endpoints.
